# 架构与迁移范围

## 部署模型

首个生产部署包含三个可独立部署的 Go 二进制程序：

- **API** 负责同步 HTTP 请求：身份认证、运营后台、大厅、配置、游戏指令和钱包指令。
- **Worker** 负责可靠的异步任务：轮次状态流转、结算、佣金、UTC 每日排行榜快照、outbox 发布、充值确认和提现对账。PQPA 提现完成后优先由 Webhook 更新；若回调丢失，Worker 会主动查询所有 `broadcasted` 订单并补偿为成功或失败状态。
- **实时网关** 负责 WebSocket 连接、房间、在线状态和客户端通知。

它们从同一源代码仓库和同一个 PostgreSQL 集群起步。每个模块都有明确的职责边界，并通过应用接口或可靠事件进行通信。只有当模块需要独立扩缩容、部署、持久化或故障隔离时，才将其拆分为独立服务。

## 当前系统能力归属

| 现有能力 | 新归属模块 | 主要一致性规则 |
| --- | --- | --- |
| 账号、密码登录、角色及会话 | Identity | 会话必须可撤销，密码必须使用 Argon2id；登录失败计数和临时锁定持久化到 PostgreSQL，供多 API 实例共享；严禁使用 MD5。 |
| 玩家与 GM API | API / Operations | 对特权指令实施 RBAC，并保留不可变审计日志。 |
| 余额、扣除投注、派奖、退款、充值及提现 | Wallet | 账本记录与余额更新必须处于同一个 PostgreSQL 事务中。 |
| 轮次、停止投注、TRON 哈希结果及结算 | Game / Worker | 六个赔率房间通过 `game_room_types` 共享 9/13/17/19/23/29 六套轮次。哈希 N 以当前高度的下一个 N 整倍数为目标块并保存为轮次号，提前 5 秒封盘；目标区块到达后立即结算，不增加固定延迟。投注保存房间、玩法及赔率快照。TRON 区块优先通过官方 TronGrid FullNode gRPC 查询，官方 HTTP API 仅在 gRPC 失败时回退。通过轮次版本和唯一结算键保证结算幂等。哈希房间、玩法和轮次均由系统维护，后台不能通过通用接口增删或人工创建。 |
| 代理层级与返水 | Agent / Worker | 佣金来源必须是已结算投注，且只能被唯一记录一次。 |
| 聊天、客服、红包及推送 | Realtime | 消息先持久化再通过 NATS 扇出；红包扣款、领取和过期退款必须与钱包账本及 outbox 位于同一事务。 |
| TRON 监听、K 线订阅和 PQPA 回调 | Chain / Worker | 必须验证回调签名、服务商事件 ID 和交易哈希，并保证幂等。 |
| 上传与对象存储 | Operations | S3 兼容存储凭证仅保留在服务端；客户端使用短时 SigV4 PUT URL，服务端通过 HEAD 核对类型和大小后才确认元数据。 |
| 定时任务与脚本 | Worker | 使用可靠的任务状态、重试、退避和死信处理机制。 |

链上提现申请还必须在锁定钱包的同一事务中检查单笔限额和 UTC 自然日累计限额。重复幂等键应先返回原申请，避免策略调整导致已受理请求重试失败。

玩家端和管理后台的刷新会话必须持久化所属端。令牌轮换时同时检查会话端和用户当前角色，角色变更后不再符合所属端规则的会话立即撤销。
后台角色变更仅允许 `admin` 执行，更新后撤销目标账号全部刷新会话；禁用账号同样撤销其刷新会话。系统禁止管理员移除自己的 admin 角色或禁用自己，也禁止移除或禁用平台最后一个有效 admin。

平台动态配置以 JSON 保存，并明确区分 `public` 与 `internal`。公开接口只返回
`public` 配置；后台更新必须提交期望版本号，通过乐观锁避免多个管理员相互覆盖。
第三方密钥、密码和令牌不得写入平台配置表。

## 必需的事务模式

共享客服话术归 Operations，独立存储于 `customer_phrases`（0051）。话术权限开放给当前 admin/operator，仍复核数据库账号状态及角色；话术仅为手动发送聊天的文本模板，不进入自动回复或消息推送链路。全部写操作按同一短事务锁串行化，保证全局重排与新增/编辑/删除不交错，变更和审计同事务。列表计数与分页采用同一只读快照；创建按操作人及request_id幂等，删除标记保留创建键防止旧请求复活记录。

### 币种目录与统一账本

人工上下分统一由 Credit 应用服务处理。`POST /v1/admin/wallet-adjustments` 与旧上分入口允许 admin/operator，并在请求内验证后台全局一级密码 first_password；应用服务复核数据库当前角色。0049 保存按 `(operator_id,request_id)` 唯一的操作参数与结果，余额、流水、成功审计、幂等结果和 outbox 同事务。仅修改可用余额，不影响冻结资金，不触发链上付款。虚拟账户禁止人工扣款；真实账户人工上分、清退、赠分、扣分分别统计，成功提现仅按最终扣款流水计入清退，不能再次累计申请/冻结记录。

`currencies` 是平台币种和精度的唯一目录。保留 UUID 主键，但现有领域外键引用其唯一 `code`，不在同一记录中维护两套可独立修改的币种标识。数据库禁止修改币种代码/精度，以及钱包的所属用户/币种；新增币种不会改变已有余额单位。

所有资产共用 `wallets` 和 `ledger_entries`。0045 将积分、体力旧账本搬入统一账本并删除旧表；保留原流水 ID、金额、时间、备注、操作人，不按残缺历史重算余额。流水区分业务金额、可用余额增量、冻结余额增量及事后快照。历史冻结余额无法还原时为 NULL。

新流水通过数据库触发器在同一事务追加 `wallet.ledger.committed` outbox 事件；应用仍须先锁钱包并更新余额，再追加流水。原业务事件保留，消费者不得将两种事件都视为一笔新的入账指令。

网络精度属于 `provider_supported_assets`；平台精度属于 `currencies`。充值保存原始金额及两种精度，提现保存提交时精度，不因服务商刷新配置而改写在途单。无法精确转换时拒绝，不取整或四舍五入。

活动领取、转盘结果及排行榜发奖保留配置快照，历史未知快照为 NULL。排行榜启用奖励区间使用数据库排斥约束防止重叠。任务领取锁配置行，抽奖持共享配置锁，避免同一结果混用更新前后的配置。

这些迁移需要维护窗口：旧 API/Worker 不可与 0045 后的表结构混跑。先备份、停止写入，再迁移并启动同版本三个进程；恢复旧代码必须同时恢复迁移前数据库。详见 `docs/database-optimization.md`。

处理投注请求时，API 必须在**同一个**事务中锁定钱包行、校验可用余额、创建投注、追加账本扣款记录、更新钱包余额，并追加一条 outbox 事件。Worker 只能处理已提交的 outbox 记录。这样可以避免将数据库写入和 Redis 发布误认为同一操作而产生的数据不一致问题。

## 计划中的接口

- 外部 API：采用 REST/JSON 和 OpenAPI，使用 JWT 访问令牌与幂等键。
- 内部同步调用：模块尚未独立部署时优先使用 Go 接口；独立部署后使用 ConnectRPC/gRPC。
- 内部异步调用：使用 NATS JetStream 主题，例如 `game.bet.placed`、`game.round.settled`、`wallet.ledger.committed`、`chain.deposit.credited`。
- 实时协议：使用经认证的 WebSocket v1 消息；支持全局游戏与指定轮次订阅，钱包和链上事件按用户定向发送，并以有界发送队列隔离慢连接。

## 拆分触发条件

1. 当连接数量需要独立扩缩容时，拆分 `realtime`。
2. 当服务商故障或签名控制需要隔离时，拆分 `chain`。
3. 当轮次处理需要独立容量或发布节奏时，拆分 `game-settlement`。
4. 只有在账本接口稳定且能独占数据库所有权后，才拆分 `wallet`。

后台全局操作密码由 adminsecurity 应用服务负责，0050 将 first/second 密码哈希和按账号/用途的失败锁定记录独立存储。仅 admin 验证自己的登录密码后可设置或重置；个人二级密码不变。敏感配置更新验证 second_password，传递业务请求前移除密码，避免写入配置及审计。密码修改与审计同事务提交；不引入 super_admin 角色。
