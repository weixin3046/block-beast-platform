# 架构与迁移范围

## 部署模型

0067 单登录会话：身份仓储在用户行锁内撤销旧 sessions 并创建新会话，部分唯一索引保证每用户最多一条未撤销会话。JWT sid 绑定稳定 sessions.id，刷新只轮换凭据；HTTP 与 Realtime 共用身份领域会话校验，数据库异常拒绝放行。Realtime 在握手、命令以及每秒检测中校验；不依赖单进程内存完成跨实例踢出。升级撤销历史会话，API/Realtime 必须协调更新。

首个生产部署包含三个可独立部署的 Go 二进制程序：

- **API** 负责同步 HTTP 请求：身份认证、运营后台、大厅、配置、游戏指令和钱包指令。
- **Worker** 负责可靠的异步任务：轮次状态流转、结算、佣金、UTC 每日排行榜快照、outbox 发布、充值确认和提现对账。PQPA 提现完成后优先由 Webhook 更新；若回调丢失，Worker 会主动查询所有 `broadcasted` 订单并补偿为成功或失败状态。
- **实时网关** 负责 WebSocket 连接、房间、在线状态和客户端通知。

它们从同一源代码仓库和同一个 PostgreSQL 集群起步。每个模块都有明确的职责边界，并通过应用接口或可靠事件进行通信。只有当模块需要独立扩缩容、部署、持久化或故障隔离时，才将其拆分为独立服务。

链上提现申请还必须在锁定钱包的同一事务中检查单笔限额和 UTC 自然日累计限额。重复幂等键应先返回原申请，避免策略调整导致已受理请求重试失败。

玩家端和管理后台的刷新会话必须持久化所属端。令牌轮换时同时检查会话端和用户当前角色，角色变更后不再符合所属端规则的会话立即撤销。
后台角色变更仅允许 `admin` 执行，更新后撤销目标账号全部刷新会话；禁用账号同样撤销其刷新会话。系统禁止管理员移除自己的 admin 角色或禁用自己，也禁止移除或禁用平台最后一个有效 admin。

平台动态配置以 JSON 保存，并明确区分 `public` 与 `internal`。公开接口只返回
`public` 配置；后台更新必须提交期望版本号，通过乐观锁避免多个管理员相互覆盖。
第三方密钥、密码和令牌不得写入平台配置表。

## 必需的事务模式

0066提供事务内客服房间初始化函数，真实player注册和后台创建账号在分配角色后调用；房间和owner成员与账号一起提交或回滚。函数与现有懒创建共用按用户advisory锁和房间唯一索引。迁移为历史真实player补建缺失房间，不重建已有会话，不自动为虚拟账号建房。部署需先迁移再启动新版API。

### 哈希订单与逐次下单记录（0064）

新哈希订单按玩家、轮次、钱包币种、房间、玩法及 pick 合单，仅accepted可追加，partial unique index兜底。下单沿用用户→轮次→投注→钱包锁，取消/作废/结算锁轮次后不会与追加交错。bet_placements保存每次增量、请求编号及机器人计划，(user_id,client_request_id)与(plan,round)唯一；账本business_id仍引用稳定订单ID，bet_placement_id区分每次扣款。其他账本业务的原唯一语义保留。追加、扣增量余额、不可变账本与outbox同事务。

合单保留首单created_at、赔率与返水快照；placement_count和last_placed_at记录追加版本/时间。结算及退款按总本金一次执行，保留原资金/模拟属性。历史单只回填请求记录，不合并、不改旧账本；新订单merge_enabled显式启用。升级停止旧写入后执行0064，同版本三个进程一起启动。公开事件含最新合单和增量added_stake，消费者不能用合计额再次累加。

### 参考级差返水（本地接入，尚未部署）

`rebate` 模块提供千分比级差计算与版本化配置。0060初始化六房间、六哈希玩法、四投注币种的144组旧配置；0083 将新投注使用的配置收敛为每个赔率房间一份，所有币种和哈希玩法共用。迁移按每房间最后更新时间最新的旧行初始化，保留旧矩阵和历史快照供审计；配置变更和审计同事务，后台GET/PUT rebate-configs写入需admin/operator及后台二级密码。

0061增加投注返水版本、下单快照及发放明细。新版API在下单事务中为哈希投注保存配置版本、上级链、等级和比例，并标记版本2；未配置、停用配置和模拟单不会回退到旧佣金。版本1历史单保留旧直属佣金逻辑，不追溯补差。版本2正常结算按快照计算级差，所有玩法均使用投注本金；虚拟收款人跳过。每笔投注/收款人唯一，余额、commission账本、明细及账本触发的outbox在结算事务中提交，仍使用原commission分类避免统计重复。

结算先锁轮次及投注，收集全部玩家/收款人，补齐缺失钱包后按钱包UUID统一加锁；玩家取消也先锁轮次，避免与结算逆序。升级必须停止旧API/Worker写入，依次应用0060–0063，再启动同版本进程，禁止旧Worker处理版本2订单。专用返水明细查询/统计使用同一只读快照，按币种统计并排除模拟及虚拟用户；进度详见 `reference-alignment-progress.md`。

0062提供后台单笔作废：轮次→投注→钱包锁，与结算互斥；余额、账本、操作记录、审计和outbox原子提交。只允许accepted变voided，不能撤销已结算输赢。作废退款为bet_void分类，不统计为充值/赠分。普通玩家创建复用密码身份/头像验证/零钱包初始化，仅赋player；绑定上级、玩家绑定与注册共用代理图事务锁，禁止改挂、成环并维护后代路径。

0063存储用户/IP白名单。按用户确认，第三方IP及设备风险检测暂不接入；API显式返回未启用和豁免未生效状态，不使用白名单绕过密码、账号禁用、失败锁定或角色权限。

### 虚拟账户与机器人计划

0055 引入 `robot_plans`，API 负责 admin/operator 计划管理，Worker 按共享哈希轮次序号调度。同一用户可配置多个房间/币种计划；计划行锁、模拟投注和下一期号在同一事务提交，另以 `(robot_plan_id,round_id)` 唯一约束防止重复下单。首次观察或错过目标期号只安排未来期号，不补历史单。旧固定秒数 automation 接口返回 410，不自动转换旧计划。

新虚拟账户投注在创建时保存 `bets.is_simulated=true`；不扣钱包，中奖、取消、退款也不增加钱包，不产生投注资金流水、代理佣金或活动累计。历史订单的标记默认为 false，继续按原真实资金链路结算，不能按用户当前类型推断订单资金属性。模拟输赢用于混合排行榜，保留虚拟玩家标识且占据排名和奖励位置；排行榜奖励是独立业务，不等同于模拟投注派奖。真实看板与代理团队统计排除虚拟账户；虚拟账户禁止下分和红包收发。

升级必须先停止旧 API/Worker 写入，按顺序执行 0054、0055，再启动同版本进程并创建新计划。旧 Worker 不识别模拟标记，不能与新版本混跑，否则存在模拟订单被错误派奖的风险。不需要清空真实余额或历史账本。

共享客服话术归 Operations，独立存储于 `customer_phrases`（0051）。话术权限开放给当前 admin/operator，仍复核数据库账号状态及角色；话术仅为手动发送聊天的文本模板，不进入自动回复或消息推送链路。全部写操作按同一短事务锁串行化，保证全局重排与新增/编辑/删除不交错，变更和审计同事务。列表计数与分页采用同一只读快照；创建按操作人及request_id幂等，删除标记保留创建键防止旧请求复活记录。

### 活动任务与转盘生命周期

0056将转盘删除改为软删除，抽奖与删除/编辑锁同一配置行，历史抽奖仍引用原配置。转盘启停相互独立，禁用奖项不进入权重池；停止公共整批保存入口，避免遗漏配置被连带停用。中奖列表只展示已执行抽奖记录，标识虚拟账户，不合成中奖流水。

0057新增每用户、任务、周期的独立进度及多奖励配置；0058保存领取时完整规则快照，0059清除已经发奖的末轮进度，避免提升上限后重复领取。每日任务使用投注创建时间所在中国日期，长期任务使用固定周期键；只在非模拟、非躲避订单最终结算为输/赢时累计。达标封顶，手动领取后进入下一轮，达到配置次数上限停止；每日未领取过期，不补领跨午夜晚结算的旧日奖励。奖励余额、所有奖励流水、领取记录与进度次数同事务，领取按钱包再进度的顺序加锁。任务有进度后不可改变累计币种/周期，删除保留审计历史。

0056–0059需要停止旧API/Worker写入后顺序迁移、启动同版本进程；旧共享进度和旧领取表仅保留历史记录，不再参与新累计或领取。

人工上下分统一由 Credit 应用服务处理。`POST /v1/admin/wallet-adjustments` 与旧上分入口允许 admin/operator，并在请求内验证后台全局一级密码 first_password；应用服务复核数据库当前角色。0049 保存按 `(operator_id,request_id)` 唯一的操作参数与结果，余额、流水、成功审计、幂等结果和 outbox 同事务。仅修改可用余额，不影响冻结资金，不触发链上付款。虚拟账户禁止人工扣款；真实账户人工上分、清退、赠分、扣分分别统计，成功提现仅按最终扣款流水计入清退，不能再次累计申请/冻结记录。

`currencies` 是平台币种和精度的唯一目录。保留 UUID 主键，但现有领域外键引用其唯一 `code`，不在同一记录中维护两套可独立修改的币种标识。数据库禁止修改币种代码/精度，以及钱包的所属用户/币种；新增币种不会改变已有余额单位。

所有资产共用 `wallets` 和 `ledger_entries`。0045 将积分、体力旧账本搬入统一账本并删除旧表；保留原流水 ID、金额、时间、备注、操作人，不按残缺历史重算余额。流水区分业务金额、可用余额增量、冻结余额增量及事后快照。历史冻结余额无法还原时为 NULL。

新流水通过数据库触发器在同一事务追加 `wallet.ledger.committed` outbox 事件；应用仍须先锁钱包并更新余额，再追加流水。原业务事件保留，消费者不得将两种事件都视为一笔新的入账指令。

网络精度属于 `provider_supported_assets`；平台精度属于 `currencies`。充值保存原始金额及两种精度，提现保存提交时精度，不因服务商刷新配置而改写在途单。无法精确转换时拒绝，不取整或四舍五入。

活动领取、转盘结果及排行榜发奖保留配置快照，历史未知快照为 NULL。排行榜启用奖励区间使用数据库排斥约束防止重叠。任务领取锁配置行，抽奖持共享配置锁，避免同一结果混用更新前后的配置。

这些迁移需要维护窗口：旧 API/Worker 不可与 0045 后的表结构混跑。先备份、停止写入，再迁移并启动同版本三个进程；恢复旧代码必须同时恢复迁移前数据库。详见 `docs/database-optimization.md`。

处理投注请求时，API 必须在**同一个**事务中锁定钱包行、校验可用余额、创建投注、追加账本扣款记录、更新钱包余额，并追加一条 outbox 事件。Worker 只能处理已提交的 outbox 记录。这样可以避免将数据库写入和 Redis 发布误认为同一操作而产生的数据不一致问题。

## 计划中的接口

- 外部 API：采用 REST/JSON 和 OpenAPI，使用 JWT 访问令牌与幂等键。
- 内部同步调用：模块尚未独立部署时优先使用 Go 接口；独立部署后使用 ConnectRPC/gRPC。
- 内部异步调用：使用 NATS JetStream 主题，例如 `game.bet.placed`、`game.round.settled`、`wallet.ledger.committed`、`chain.deposit.credited`。
- 实时协议：使用经认证的 WebSocket v1 消息；支持全局游戏与指定轮次订阅，钱包和链上事件按用户定向发送，并以有界发送队列隔离慢连接。

## 拆分触发条件

1. 当连接数量需要独立扩缩容时，拆分 `realtime`。
2. 当服务商故障或签名控制需要隔离时，拆分 `chain`。
3. 当轮次处理需要独立容量或发布节奏时，拆分 `game-settlement`。
4. 只有在账本接口稳定且能独占数据库所有权后，才拆分 `wallet`。

后台全局操作密码由 adminsecurity 应用服务负责，0050 将 first/second 密码哈希和按账号/用途的失败锁定记录独立存储。仅 admin 验证自己的登录密码后可设置或重置；个人二级密码不变。敏感配置更新验证 second_password，传递业务请求前移除密码，避免写入配置及审计。密码修改与审计同事务提交；不引入 super_admin 角色。

## LULU 外部彩石通道（0069）

`application/lulu` 编排充提订单，统一 `wallets`/`ledger_entries` 为唯一余额来源；`platform/lulu` 仅适配上游协议。`cmd/lulu-worker` 使用通道级 PostgreSQL 会话锁独占采集与转赠，无需给普通消息消费者增加可重试的转赠处理。

噜噜使用 ORIGIN_STONE 钱包，精度 3，彩石 1:1；转赠只接受整数，每彩石记为 1000 最小单位。上分按订单（允许转赠早于下单最多 3 分钟）的收款号、转出 UID、数量和有效时间匹配实际流水后自动入账，不要求账号长期绑定或后台审核；该策略不构成 UID 归属验证。流水归属、余额、账本和触发器 outbox 同事务提交。

下分申请冻结，后台全局一级密码审核后排队；转赠前持久化 sending，成功才扣冻结额。超时/不明报文/重启遗留 sending 转 unknown，禁止自动重发或自动解冻，管理员核对后通过专用接口审计确认。配置默认关闭，上游地址与密钥无默认值，不迁移旧项目的敏感数据。详细边界见 [LULU 接入说明](lulu-integration.md)。

0070 将 LULU 收付 UID 和启用状态集中到单例 lulu_config。配置修改仅 admin，HTTP 验证全局二级密码后移除密码，应用层再次验证角色；版本锁、前后值审计同事务。新单与派发对配置行持共享事务锁，配置更新独占锁，防止旧账号新建/派发穿过切换。切换账号前需先停用并清空在途订单，历史 UID 快照不变。worker 常驻每轮刷新数据库配置，停用不退出；升级必须停旧 worker，避免旧账号锁与新通道锁共存。

0071 在 lulu_config 增加上游地址、采集起始时间和 AES-GCM 加密的 Token/协议密钥。应用层从服务器 LULU_CONFIG_ENCRYPTION_KEY 解密，HTTP 与审计只暴露配置状态，所有密码在 HTTP 验证后移除。worker 每轮读取一个完整版本的运行配置，派发事务复核版本防止旧凭据快照派发。原环境变量及 Token 文件不再作为生产运行配置源。升级暂停通道，补齐凭据后由管理员重新启用。

# 钱包事件发布唤醒（0079）

0081 将公开用户ID和邀请码统一为五位数10001–99999，保留内部UUID及所有资金关系。历史用户按旧public_id顺序分配新编号，user_public_id_history保存映射。同步排行榜公开ID、机器人create_input、作废结果缓存和未发布outbox中的公开ID；历史审计和已发布事件保留原值。序列达到99999拒绝继续分配，不循环覆盖。升级先停止API/Worker/Realtime，迁移后启动同版服务，前端刷新资料及缓存，旧公开ID不再接受。

0080 引入 scheduled 轮次状态：调度预创建三期，但只有最早未完成轮次可开放。closed/settling 阻止后继开放，settled/cancelled 后 Worker 激活下一期。调度与激活共用事务锁；下注在轮次锁内检查状态及更早未完成轮次，机器人按期号升序选择。已过封盘时间的 scheduled 直接封盘并进入正常结算；既有投注和资金不回写。迁移将历史多开的后续轮次转为 scheduled。升级须停旧 API/Worker 后迁移并更新，禁止旧 Worker 继续创建 open 轮次。
